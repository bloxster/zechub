# zecd — خادم محافظ يعطي الأولوية للمعاملات المحمية

zecd هو خادم محفظة (wallet) يعطي الأولوية للمحمي (shielded) لـ Zcash، وهو مبني على [librustzcash](https://github.com/zcash/librustzcash) ومُتاح عبر لهجة JSON-RPC الخاصة بـ Bitcoin Core. يمنح المطورين (developers) ومُدمجي المدفوعات (payments) واجهة API مألوفة ومتوافقة مع Bitcoin للتفاعل مع Zcash، مع جعل Orchard (المجمّع (pool) الأكثر خصوصية) الخيار الافتراضي. طوّره [zec.rocks](https://zec.rocks)، وقد صُمّم zecd ليحل محل وظائف المحفظة في `zcashd` ضمن عمليات النشر الحديثة الأصلية السحابية.

**الإصدار الحالي:** 0.5.0-rc3 (13 يوليو 2026) مع دعم Ironwood (NU6.3). ثبّته عبر `cargo install zecd` أو استخدم صورة Docker الرسمية.

---

## الخلاصة (TL;DR)

- zecd هو **برنامج خدمي للمحفظة (خادم)**، وليس عقدة كاملة (full node). يتولى المفاتيح والمسح وإنشاء البراهين وواجهة RPC دون التحدث ببروتوكول P2P الخاص بـ Zcash.
- يتحدث **لهجة JSON-RPC الخاصة بـ Bitcoin Core**: أسماء الطرق نفسها، وأشكال الحقول نفسها، والمصادقة ورموز الأخطاء نفسها. لذلك تعمل كثير من عملاء Bitcoin RPC مع Zcash مباشرةً دون تعديل.
- **عناوين (addresses) Orchard (المحمية) هي الافتراضية**؛ أما دعم العناوين الشفافة (transparent) (t-address) ودعم Sapling فيتطلبان تفعيلاً صريحاً لكل محفظة.
- يتصل **بعقدة كاملة [Zebra](Zebra_Full_Node.md) مُستضافة ذاتياً** عبر JSON-RPC محلي، دون حاجة إلى lightwalletd.
- **عديم الحالة بالتصميم**: يمكن استعادة المحفظة بالكامل من عبارة البذور (seed phrase) وحدها، مما يجعل دليل البيانات قابلاً للاستغناء عنه.
- **ليس بديلاً مباشراً لـ zcashd**: ينفّذ مجموعة فرعية فقط من طرق RPC في Zcash، مع اختلافات تصميمية مقصودة من أجل الخصوصية (privacy) والأمان.
- تتبع الرسوم (fees) معيار **ZIP-317** (حساب رسوم حتمي)؛ وتُرفض الرسوم التي يحددها المستخدم.
- يدعم **المذكرات (memos) المحمية (ZIP-302)** عبر واجهة Bitcoin RPC المألوفة.

## ما المشكلة التي يحلها zecd؟

كان `zcashd` هو العقدة (node) والمحفظة الأصليتين لـ Zcash مجتمعتين في برنامج واحد، وقد انشق عن قاعدة شيفرة Bitcoin المكتوبة بلغة C++ في عام 2016. ومع مرور الوقت، أدى ذلك إلى صعوبات: فالشيفرة صعبة الصيانة، والمحفظة مرتبطة بإحكام بالعقدة، والعناوين الشفافة تُعرض خياراتٍ من الدرجة الأولى إلى جانب العناوين المحمية.

يفصل zecd مسؤولية المحفظة عن الإجماع (consensus). إنه **طبقة محفظة مخصصة** تقع بين التطبيقات وعقدة كاملة Zebra، وتوفر:

- تنفيذاً نظيفاً وحديثاً بلغة Rust مبنياً على librustzcash (المكتبة نفسها التي تشغّل Zodl وـ Zingo)
- تصميماً يجعل الخصوصية هي الوضع الافتراضي (عناوين Orchard ما لم يُضبط خلاف ذلك)
- واجهة RPC متوافقة مع Bitcoin تُغني عن تعلّم أدوات (tools) خاصة بـ Zcash
- بنية عديمة الحالة قابلة للاستعادة من البذور، مناسبة لعمليات النشر في الحاويات والسحابة

## البنية

يعمل zecd وفق نموذج من ثلاث طبقات:

```
Your app / Bitcoin RPC client
        ↓  JSON-RPC
       zecd
   (keys, scanning, proving, RPC)
        ↓  JSON-RPC (local only)
       Zebra
   (full node — consensus, mempool, chain data)
```

يتواصل zecd مع Zebra **حصرياً عبر JSON-RPC محلي**، دون شبكات نظير إلى نظير، ودون مفهرسات من أطراف ثالثة، ودون lightwalletd. اتصال Zebra محلي فقط عن قصد: سيرفض zecd إرسال بيانات الاعتماد إلى مضيف قابل للتوجيه عالمياً ما لم يُضبط صراحةً لاستخدام نفق مؤمَّن خارج النطاق (مثل WireGuard أو SSH).

## الميزات الرئيسية

### الأولوية للمحمي، وـ Orchard افتراضياً

يستخدم zecd عناوين Orchard الموحّدة (Unified Addresses) نوعاً افتراضياً للعناوين. تتطلب مجمّعات Sapling والمجمّعات الشفافة (t-address) ضبطاً صريحاً لكل محفظة. يقلّل هذا التصميم من خطر الإرسال الشفاف عن طريق الخطأ، وهو خطأ شائع يمس الخصوصية في أدوات Zcash الأقدم.

يمكن ضبط سياسة الخصوصية لكل استدعاء على حدة أو بشكل عام في `[spend] privacy_policy`:

| السياسة | السلوك |
|--------|----------|
| `AllowRevealedRecipients` (افتراضي) | تسمح بالإرسال إلى مستلمين شفافين؛ وتكشف المبلغ والمستلم على السلسلة (on-chain) |
| `AllowRevealedAmounts` | تسمح بالإرسال عبر المجمّعات (Sapling↔Orchard) لكنها ترفض المستلمين الشفافين |
| `FullPrivacy` | تسمح فقط بالإرسال المحمي بالكامل داخل مجمّع واحد؛ وترفض المستلمين الشفافين والإرسال عبر المجمّعات |
| `AllowFullyTransparent` | تسمح أيضاً بالإرسال t→t الممول من UTXOs شفافة |

### التوافق مع Bitcoin Core RPC

ينفّذ zecd لهجة JSON-RPC الخاصة بـ Bitcoin Core ويتوافق معها في:

- أسماء الطرق (مثل `getblockchaininfo`، `getbalance`، `getnewaddress`، `listtransactions`، `sendtoaddress`، `sendmany`)
- أسماء الحقول وأنواعها في الاستجابات
- بنية مغلّف JSON-RPC 1.0
- المصادقة الأساسية، ومدخلات `rpcauth`، والمصادقة بملف cookie
- رموز الأخطاء وربطها بحالات HTTP (HTTP 500 مع جسم الخطأ، ودلالات 401)

هذا يعني أن كثيراً من مكتبات مدفوعات Bitcoin الحالية، وتكاملات منصات التداول (exchanges)، وأدوات المراقبة يمكنها التفاعل مع Zcash عبر zecd بتغييرات قليلة في الشيفرة أو دونها.

تعمل حزمة اختبارات التوافق (أكثر من 140 فحصاً) على كل طلب سحب (PR) مقابل برنامج خدمي حي على regtest، كما جرى التحقق منها مقابل شبكة الاختبار العامة.

### المذكرات المحمية (ZIP-302)

يتيح zecd ميزة المذكرات المحمية في Zcash عبر واجهة Bitcoin RPC المألوفة، وهي ميزة غير متاحة في أدوات Bitcoin القياسية:

- يقبل `sendtoaddress` مذكرة اختيارية بصيغة hex كمعامل إضافي في النهاية (حتى 512 بايت؛ وتُرفض للمستلمين الشفافين)
- تتضمن مدخلات سجل المعاملات (transactions) من `listtransactions` وـ `gettransaction` حقلي `memo` (hex) وـ `memoStr` (النص بعد فك ترميزه) عندما يحمل المُخرَج مذكرة
- الإرسال بمبلغ صفري إلى مستلم محمي مدعوم لحالات الاستخدام (use cases) الخاصة بالمذكرات فقط (نمط «memo-only-send» في `z_sendmany`)

يجعل هذا zecd مناسباً للتطبيقات التي تحتاج إلى مراسلة خاصة على السلسلة إلى جانب المدفوعات.

### عديم الحالة بالتصميم

لا يحتفظ zecd **بأي حالة خارج السلسلة يتعذّر إعادة بنائها عند الاستعادة من البذور وحدها**. قاعدة بيانات المحفظة (`data.sqlite`) قابلة للاشتقاق بالكامل من عبارة البذور: تُستعاد الأموال المحمية دون قيد أو شرط، وتُستعاد الأموال الشفافة حتى حد الفجوة (gap limit) المضبوط.

لاستعادة محفظة من البذور:

```sh
zecd init --restore --birthday <block-height>
```

يجعل هذا دليل البيانات **قابلاً للاستغناء عنه**: الحاوية التي لا تملك وحدة تخزين دائمة، والتي يُعاد بناؤها من البذور عند كل تشغيل، لا تفقد شيئاً جوهرياً. يتحمّل المشغّلون مسؤولية تتبّع العناوين التي يوزعونها، إذ لا يتذكر zecd العناوين إلا بعد أن تتلقى أموالاً على السلسلة.

التسميات (labels) غائبة عن قصد. فبما أن التسميات ليس لها مصدر على السلسلة ولا يمكن إعادة بنائها من البذور، فإن zecd ببساطة لا يدعمها. يؤدي استدعاء طرق التسميات إلى إرجاع خطأ `method-not-found` (`-32601`).

### لا اعتماد على lightwalletd

يشتق zecd الكتل (blocks) المضغوطة وحالة الشجرة ورؤية mempool مباشرةً من JSON-RPC الخاص بـ Zebra. لا يوجد lightwalletd يلزم تشغيله أو صيانته، مما يقلل التعقيد التشغيلي لعمليات النشر المستضافة ذاتياً.

### عمليات نشر أصلية سحابية وفي حاويات

صُممت البنية عديمة الحالة لـ zecd لبيئات Docker وـ Kubernetes:

- مجموعة Docker Compose كاملة (`zebra → zecd`) متاحة في المستودع
- نقطة نهاية لفحص الصحة على المنفذ `9233` مع فحوص جاهزية قابلة للضبط (`synced` أو `connected`)
- خيار تسجيل بصيغة JSON منظَّمة لخطوط تجميع السجلات
- رسوم ZIP-317 حتمية، دون حاجة إلى أوراكل رسوم أو ضبط يدوي للرسوم
- `bootstrap_from_keys` (مفعّل افتراضياً): يؤدي وجود دليل بيانات فارغ بجوار `keys.toml` إلى إعادة بناء المحفظة تلقائياً عند بدء التشغيل؛ يمكنك النشر بتحميل Secret واحد والبدء بـ PVC فارغ

## نماذج حفظ المفاتيح

يدعم zecd ثلاثة نماذج لحفظ المفاتيح، يناسب كل منها متطلبات نشر وأمان مختلفة:

### 1. غير مشفّر (الافتراضي — فتح تلقائي)

تُغلَّف عبارة الاسترجاع في `keys.toml` بـ **ملف هوية age** (`identity.txt`). مع الإعداد الافتراضي `auto_unlock = true`، يُفك تشفير (encryption) البذور في الذاكرة عند بدء التشغيل، فتتم عمليات الإرسال دون تدخل ولا حاجة إلى استدعاء `walletpassphrase`.

الأنسب لـ: معالجات المدفوعات الآلية، والمحافظ الساخنة لمنصات التداول، وبيئات المطورين.

```sh
zecd init --datadir ./data --wallet default --account-name primary
```

> خزّن `identity.txt` **خارج** دليل البيانات على الشبكة الرئيسية، فأي شخص يقرأ الملفين معاً يملك صلاحية الإنفاق.

### 2. مشفّر (مؤمَّن بعبارة مرور)

تُغلَّف عبارة الاسترجاع بعبارة مرور (age scrypt) بدلاً من ملف هوية. تبدأ المحفظة مقفلة؛ ويفتحها `walletpassphrase "<pass>" <timeout>` للمدة المحددة ثم يعيد قفلها تلقائياً عند انتهاء المهلة، بما يطابق سلوك المحفظة المشفّرة في Bitcoin Core.

الأنسب لـ: المحافظ الساخنة التي لا تتطلب صلاحية إنفاق دون تدخل، وسير عمل المشغّلين التفاعلي.

```sh
zecd init --datadir ./data --encrypt
# later: walletpassphrase "my-passphrase" 300
```

### 3. للمراقبة فقط (UFVK — دون مفتاح إنفاق)

تُهيَّأ بمفتاح Unified Full Viewing Key (UFVK) مُصدَّر من محفظة أخرى. يمكنها الاستلام والمسح والإبلاغ عن الأرصدة، لكنها لا تستطيع توقيع المعاملات. وهي مثالية للمراقبة أو الفوترة أو لعقد التدقيق المنفصلة عن محفظة التوقيع.

```sh
# On the signing wallet's host:
zecd export-ufvk

# On the watch-only host:
zecd init --datadir ./data-watch --ufvk "uview1..." --birthday <height>
```

## النسخ الاحتياطي والاستعادة

يمكن استعادة الأموال من **عبارة الاسترجاع وحدها**. وكل ما عدا ذلك ذاكرة مؤقتة.

| العنصر | الموقع | ما يحميه | هل تنسخه احتياطياً؟ |
|----------|----------|-----------------|----------|
| **عبارة الاسترجاع من 24 كلمة** | تُعرض مرة واحدة عند `zecd init` | الأموال، وفقدانها = خسارة دائمة | **نعم، دون اتصال (ورق/HSM)** |
| `keys.toml` | `<wallet dir>/keys.toml` | البذور المشفّرة + ارتفاع الميلاد + الشبكة | **نعم، كـ Secret** |
| `identity.txt` | `[keys] age_identity` | يفك تشفير `keys.toml` (صلاحية الإنفاق) | **نعم، بشكل منفصل عن `keys.toml`** |
| ارتفاع الميلاد | داخل `keys.toml` | يجعل الاستعادة سريعة (أي ارتفاع قبل أول معاملة) | سجّله مع عبارة الاسترجاع |
| `data.sqlite` | `<wallet dir>/data.sqlite` | ذاكرة المحفظة المؤقتة، ويُعاد بناؤها من البذور عند الاستعادة | لا، قابلة للاستغناء عنها |
| `blocks/` | `<wallet dir>/blocks/` | ذاكرة مؤقتة للكتل المضغوطة | لا، لا تنقلها أبداً؛ وقد يكبر حجمها |
| `.cookie` | `<datadir>/.cookie` | ملف cookie مؤقت لـ RPC | لا، يُعاد توليده عند بدء التشغيل |

> **يجب أن يكون دليل البيانات محلياً على المضيف.** قفل المثيل الواحد في zecd (`<datadir>/.lock`) هو قفل استشاري على مستوى نظام التشغيل، ولا يمتد عبر المضيفين. لا تشارك أبداً دليل بيانات للقراءة والكتابة بين عدة أجهزة (NFS، `ReadWriteMany` في Kubernetes)، فتشغيل مثيلين من zecd سيُفسد قاعدة بيانات المحفظة. استخدم وحدات تخزين `ReadWriteOnce` في Kubernetes.

## قائمة الطرق المسموح بها في RPC

في عمليات النشر التي قد يكون فيها تسرّب بيانات الاعتماد كارثياً، يدعم zecd تقييد واجهة RPC بمجموعة فرعية مختارة من الطرق:

```toml
[rpc]
allowed_methods = ["getblockchaininfo", "getbalance", "getnewaddress", "listtransactions"]
```

أي طريقة غير موجودة في القائمة تُرجع `-32601` (HTTP 404)، ولا يمكن تمييز ذلك عن طريقة غير موجودة أصلاً، لذا لا يكشف الخادم المُقفل شيئاً عمّا عطّله. يمكن لأداة فوترة مخصصة للاستلام فقط أن تعطّل `sendtoaddress` وـ `sendmany` وـ `stop` لتقليل نطاق الضرر إذا اختُرق أحد العملاء.

## الاختلافات الرئيسية عن Bitcoin Core RPC

إذا كنت مطوراً تنتقل من أدوات Bitcoin أو zcashd، فاحرص على معرفة هذه الاختلافات المقصودة:

| السلوك | Bitcoin Core | zecd |
|----------|-------------|------|
| صيغة العنوان | `1...` / `bc1...` | `u1...` (Unified Address لـ Orchard)، ولا يمكن للعملاء الذين يعتمدون على تحليل النصوص قراءته كعنوان Bitcoin |
| التسميات | مخزن تسميات كامل | غير منفَّذة؛ `setlabel` وـ `listlabels` وغيرها تُرجع `-32601` |
| الرسوم | يضبطها المستخدم؛ سوق رسوم | ZIP-317 حتمية فقط؛ وتُرفض `settxfee` وـ `fee_rate` وـ `subtractfeefromamount` مع `-8` |
| المذكرات | غير مدعومة | يقبل `sendtoaddress` مذكرة بصيغة hex؛ ويحتوي السجل على حقلي `memo` + `memoStr` |
| التأكيدات اللازمة للإنفاق | 1 | 3 (الفكة الخاصة) / 10 (من طرف ثالث)، وهي قابلة للضبط عبر `trusted_confirmations` / `untrusted_confirmations` |
| `listsinceblock` عند إعادة التنظيم | يعود إلى نقطة الانقسام | يُرجع `-5` (Block not found) إذا أُزيل المؤشر بإعادة التنظيم؛ أعد تحديد خط الأساس باستدعاء دون معاملات |
| المستلمون المكررون في `sendmany` | خطأ | يدمج محلل JSON التكرارات (يُعتمد الأخير) قبل أن يراها zecd؛ لا تُدرج العنوان نفسه مرتين |
| الرصيد أثناء المزامنة الأولية | يتوقف عن الاستجابة أو ينتظر مرحلة الإحماء | يقدّم رصيداً جزئياً؛ اربط الأتمتة بـ `GET /readyz` (يُرجع 503 حتى تكتمل المزامنة ويُنجَز تراكم التحسينات) |
| `minconf 0` في `getbalance` | رصيد 0-conf | يُقدَّم كـ 1، إذ لا يمكن أبداً إنفاق note محمية قبل تعدينها |

## البدء السريع

**المتطلبات المسبقة:** Zebra يعمل محلياً مع `rpc.listen_addr = 127.0.0.1:18234` (شبكة الاختبار).

ثبّته من crates.io (0.4.3+):

```sh
cargo install zecd
```

أو ابنِه من المصدر:

```sh
git clone https://github.com/zecrocks/zecd && cd zecd
cargo build --release
```

```sh
# 1. Initialize a testnet wallet (generates a 24-word mnemonic and an account)
zecd --datadir ./data --testnet init --wallet default --account-name primary

# 2. Start the daemon (syncs in background, serves JSON-RPC on port 18232)
zecd --datadir ./data --testnet \
    --rpcuser zec --rpcpassword secret --rpcbind 127.0.0.1 --rpcport 18232
```

**التفاعل عبر curl:**

```sh
curl -s --user zec:secret --data-binary \
  '{"jsonrpc":"1.0","id":"1","method":"getblockchaininfo","params":[]}' \
  -H 'content-type: text/plain;' http://127.0.0.1:18232/
```

**التفاعل عبر Python (باستخدام مكتبة Bitcoin RPC):**

```python
from bitcoinrpc.authproxy import AuthServiceProxy
rpc = AuthServiceProxy("http://zec:secret@127.0.0.1:18232")
print(rpc.getblockchaininfo())
addr = rpc.getnewaddress()          # returns a u1... Orchard Unified Address
print(rpc.getbalance())
print(rpc.listtransactions("*", 20))

# Send with a shielded memo
rpc.sendtoaddress(addr, 0.001, "", "", False, "48656c6c6f205a6563617368")  # hex memo
```

**الاستعادة من البذور:**

```sh
zecd --datadir ./data init --restore --birthday 2500000
# paste your 24-word mnemonic when prompted
```

## zecd مقابل zcashd مقابل Zaino

| | zcashd | Zaino | zecd |
|--|--------|-------|------|
| الدور | عقدة كاملة + محفظة | مفهرس (يحل محل lightwalletd) | خادم محفظة فقط |
| اللغة | C++ | Rust | Rust |
| الحالة | متوقف الدعم | نشط | نشط (v0.5.0-rc3، يوليو 2026) |
| المجمّع الافتراضي | شفاف | غير منطبق | Orchard (محمي) |
| لهجة RPC | خاصة بـ zcashd | gRPC (lightwalletd) | Bitcoin Core JSON-RPC |
| يتطلب عقدة كاملة | نعم (هو نفسه) | Zebra أو zcashd | Zebra |
| الاستعادة عديمة الحالة | لا | غير منطبق | نعم (من البذور فقط) |
| المذكرات المحمية | نعم (`z_sendmany`) | غير منطبق | نعم (واجهة Bitcoin RPC) |
| للمراقبة فقط (UFVK) | نعم | نعم | نعم |
| أصلي سحابي | لا | جزئياً | نعم |
| التثبيت | بناء/ملف ثنائي | بناء | `cargo install zecd` |
